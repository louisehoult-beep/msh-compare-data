# The eClass -> category bridge

Generated by `scripts/build_eclass_map.py`, from `data/npc-eclass.json`. Output: `data/eclass-category-map.json`. Do not edit either generated file by hand — re-run the script.

## The problem

`differentiator.json` states its own rule:

> "A product is published only when it has a recorded category from the gated vocabulary AND at least one source that carries it. Comparison is locked to a single category: two products may be put side by side only where their `cat` is identical."

The Supply Disruption Tracker (page 3641) starts from an NHS Supply Chain suspended line, and a catalogue line carries no `cat` — so it cannot obey that rule. Falling back to word-overlap matching across the ~38,000-record universe produced real noise, measured live on 07/09/2026: a small nitrile examination glove offered 243 "alternatives" including sterile latex surgeons' gloves size 9.5, and one supplier (Farla Medical) appearing as an alternative on 424 of 973 suspended lines (44%).

Every suspended line does carry an `eClass` code (`sdt_fetch.py` captures it for 973/973 rows, 155 distinct codes). If eClass maps to `cat`, the Tracker can gate on category equality instead.

## The method, in three steps

**1. `scripts/resolve_npc_eclass.py`** finds every NPC in `differentiator.json` that already carries a `cat` (1,432 of them, from the file's own `nhssc` join), resolves each NPC's eClass from NHS Supply Chain's own backend search API (the same one `sdt_fetch.py` already talks to), and writes `data/npc-eclass.json`: one observation row per NPC where both an eClass and a `cat` are now known, carrying the **token overlap** that backed the original NPC-to-product join.

That overlap number matters. Measured across the 2,979 NPC lines joined inside `differentiator.json`: 1,622 (54%) rest on exactly one shared significant word between the Hub product's name and the NHS Supply Chain description, and 24 share none at all. Two real examples pulled from the live data:

- **GBUK Silicone Male External Catheter** (`cat: continence:ic`) is joined to NPC `ELA85411`, NHS Supply Chain description "Foam dressing silicone including adhesive border 10cm x 25cm" — a wound dressing, not a catheter. The only word in common is "silicone".
- The 24 zero-overlap joins include cases the task brief for this build named directly: a male external catheter joined to foam dressings, and (separately, in the wider dataset) transit wheelchairs joined to a sphygmomanometer.

A join like that is worse than no join, so `resolve_npc_eclass.py` does not filter it out itself — it **carries the overlap number on every row** so the next step can. `build_eclass_map.py` drops every 0-overlap observation before it counts anything: a 0-word join is not evidence, not even weak evidence.

**2. `scripts/build_eclass_map.py`** aggregates the surviving observations **per eClass code**, not per NPC. This is what turns individually noisy joins into a usable signal: a bad single-NPC join can flip that one NPC's vote, but it cannot flip an eClass's majority unless the eClass has very few observations behind it in the first place — which is exactly the case the confidence tiers below are built to catch and refuse.

**3. Confidence tiers.** Support for a candidate `cat` is weighted 2x per distinct NPC on a "strong" join (>=2 shared significant words) and 1x per distinct NPC on a "weak" join (exactly 1 shared word).

| Tier | Requires |
|---|---|
| **HIGH** | >=3 distinct NPCs on strong joins, the winning `cat` holds >=65% of the eClass's weighted support, and >=3 distinct NPCs total |
| **MEDIUM** | >=1 strong NPC or >=3 weak NPCs, >=60% weighted support, >=2 distinct NPCs, >=3 total observations for the eClass |
| **UNMAPPED** | anything else — no observations, or the winner never clears the floor above |

An eClass that reaches neither tier gets **no `cat`**, full stop. It is recorded in the `unmapped` block with its runner-up and share, purely so the next reviewer can see why it was refused — never as a `cat` the Tracker could accidentally read.

## Why majority vote survives the bad joins that feed it

`eClass ELA` (wound dressings, itemClass "23 - Rehabilitation and Community") is the clearest real case. It carries 90 surviving observations, split:

- **63 observations for `wound:adv`** (58 on strong joins)
- **27 observations for `marketing:content`** (15 on strong joins)

The `marketing:content` votes are not a text-matching artefact — checking the source rows shows they all come from Mölnlycke's "Mepilex Border Comfort" and "Mepilex Border Sacrum" products, which are genuinely wrongly mapped to `marketing:content` upstream, in `data/differentiator-category-map.json`'s human-curated (supplier, division) decisions. That is a real upstream data error, not something this script introduced or can fix — it is flagged here so whoever owns that map can find and correct it.

What the aggregation does do is stop that error from reaching the Tracker: `wound:adv` still holds 74.2% of the weighted support (share 0.742) and clears the HIGH bar (>=3 strong NPCs, >=65% share, >=3 total NPCs), so `ELA -> wound:adv` publishes at HIGH confidence and the `marketing:content` minority never surfaces as a mapping. The full evidence, including the runner-up, is recorded on the mapping itself:

```json
"ELA": {
  "cat": "wound:adv",
  "confidence": "high",
  "itemclass": "23- Rehabilitation and Community",
  "suspendedLines": 3,
  "evidence": {
    "strongNpcs": 58, "weakNpcs": 5, "distinctNpcs": 63,
    "supportShare": 0.742, "totalObservations": 90,
    "runnerUp": {"cat": "marketing:content", "support": 42}
  }
}
```

This is also why the HIGH tier requires a genuine supermajority (65%) rather than "more votes than anyone else": a narrower margin would have let a large enough upstream error flip the winner instead of merely showing up as a visible runner-up.

## Where the evidence runs out

Of the 155 distinct eClass codes across the 973 suspended lines, **99 have at least one usable observation** (overlap >= 1) and **38 clear a confidence tier** (20 HIGH, 18 MEDIUM), covering **351 of 973 suspended lines (36.1%)**.

That leaves 117 eClass codes, and 622 suspended lines, genuinely unmapped. The reasons split into three real categories, all recorded in `unmapped`:

1. **No observation at all** — the eClass never appears among the 1,423 resolved NPCs, because no product in `differentiator.json` happens to carry an NPC on that eClass. No amount of aggregation invents evidence that was never fetched.
2. **Some evidence, no majority** — e.g. `EGB` (orthotics/monitoring hardware): 9 observations split across four different categories (`orthotics:hosiery`, `cardiology:ecg`, `vascular:vte`, `wound:comp`), none holding more than 38.9% — genuinely ambiguous eClass, not a threshold that was set too high.
3. **Thin evidence** — 1-2 total observations, which cannot pass MEDIUM's own 3-observation floor even when every one of them agrees, because a coin that has only been flipped once proves nothing.

None of these are treated as bugs to fix by loosening the thresholds. Root rule 14: an honest 36% map, with every mapped row's evidence visible, is worth more than a complete one that would put a wrong clinical product in front of a paying member as an "alternative".

## What the Tracker gets from this

`sdt_match.py` (owned separately) can now look up a suspended line's `_eclass` in `data/eclass-category-map.json`'s `mappings` block. Where it finds a `cat`, it should search for alternatives ONLY among Differentiator products carrying that same `cat` — exactly the rule the Differentiator already enforces on itself. Where the eClass is not present in `mappings`, the honest answer is that no eClass-gated alternative can be offered yet — not a silent fall-back to word overlap, which is the failure mode this whole bridge exists to remove.

## Re-running it

```
python3 scripts/resolve_npc_eclass.py          # refresh NPC -> eClass lookups (only new NPCs, by default)
python3 scripts/build_eclass_map.py --report   # see the coverage this would produce
python3 scripts/build_eclass_map.py            # write data/eclass-category-map.json
python3 scripts/stamp_notice.py                # re-stamp the ownership notice
```

Both build steps are deterministic against a fixed `data/npc-eclass.json` — same input, same output, byte for byte (fixed key order, ties broken alphabetically by `cat`). Coverage only improves when `differentiator.json` gains more categorised NPCs for `resolve_npc_eclass.py` to resolve, or when suppressed noise in the upstream category map (like the Mölnlycke case above) gets corrected — never by changing the confidence thresholds to manufacture coverage.
